# i18n: English and German, always both

The app ships full English and German translations. `src/locales/en.ts` and
`src/locales/de.ts` are plain nested objects exported as `en` / `de`.

## The rule

**Every user-facing string goes through `t()`, and every new key is added to
both files in the same edit.**

```tsx
const { t } = useTranslation();
<Button>{t('players.addPlayer')}</Button>
```

A key present in `en.ts` but missing from `de.ts` does not fall back to English
in a useful way — German users see the raw key (`players.addPlayer`). There is
no lint rule and no test catching this. It is caught only by reading the diff.

## Checklist when adding a string

1. Add the key under the right top-level section in `en.ts` (`nav`, `theme`,
   `players`, `training`, `matches`, …). Create a new section only if none fits.
2. Add the **same key path** to `de.ts`, in the same position.
3. Use it via `t('section.key')` — never a literal.

## What counts as user-facing

Everything rendered or read aloud: labels, buttons, placeholders, table headers,
empty states, `title`/`aria-label`, confirm dialogs, and **toast messages**
(`sonner`). Error strings shown to the user are translated too — but the
`detail` text thrown by the backend is not, so translate at the call site:

```ts
toast.error(t('players.saveFailed'));
```

## What is not translated

Console logs, `data-*` attributes, test fixtures, and backend `HTTPException`
detail strings (English only, developer-facing).

## Interpolation and plurals

Use i18next interpolation rather than string concatenation, so German word order
stays translatable:

```ts
// en.ts
playersSelected: '{{count}} players selected',
```

```tsx
t('players.playersSelected', { count: selected.length })
```

## Do not

- Do not reorder or re-nest existing keys as a cleanup — every component
  referencing the old path breaks silently at runtime, not at build time.
- Do not add a third language without being asked; `i18n.ts`, the language
  detector, and the switcher all need changes together.
